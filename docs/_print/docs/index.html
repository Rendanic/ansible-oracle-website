ansible-oracle

This is the Homepage of the project ansible-oracle hosted on https://github.com/oravirt/ansible-oracle.

Automated installation of

  • Oracle RAC databases
  • RAC One Node database and
  • single instance Oracle databases
  • Start with one or more clean Linux machine(s), end up with a fully configured Oracle database system

  2. More details https://github.com/oravirt/ansible-oracle

2.1 - Vagrant

2.1.1 - Vagrant on Windows

1. Overview

Important
 This documentation describes the installation of the required tools for ansible-oracle on a Windows based hostsystem.

  • Requirements

    • Intel/AMD x86 CPU is mandatory
      no support for Mac with M1

    • 16 GB RAM

    • 150 GB free Disk space
      The free space is needed in your home directory in Windows.

    • Admin privileges on Host machine

    • Hyper-V disabled

    • no WSL/WSL2 for installation
      While you may try it, the documentation states that Hyper-V should be completely disabled and that no WSL/WSL2 is used.

Warning
 There are many issues when Hyper-V is active on the host machine.
Please switch Hyper-V off completely, before starting the boxes with Vagrant.
If you do find a really good working solution with Vagrant + VirtualBox and Hyper-V, feedback is welcome.

2. Installation

2.1. Disable Hyper-V in Windows

Warning
 There are numerous problems with Vagrant & VirtualBox when Hyper-V is enabled.
It is therefore recommended to disable it for ansible-oracle.

2.1.2 - Vagrant Basics

What is vagrant?

Vagrant is a tool that makes it EASIER and FASTER to setup virtual machines. Vagrant Boxes are pre-built base images (e.g. Oracle Linux) that can be imported into Vagrant as a starting point. For our use-case, we will use Vagrant together with Virtualbox and Oracle Linux

Installation

  1. Download and install Vagrant
  2. Download and install Oracle Virtualbox

Let’s start

Using Tim Halls’s guide, let’s play https://oracle-base.com/articles/vm/vagrant-a-beginners-guide

  1. hmm, cannot download that first OL box, let’s see the oracle doc https://yum.oracle.com/boxes/
  2. Note also that the default provider for vagrant has changed to libvirt (was virtualbox), so we will need to add “–provider virtualbox” to our vagrant add commands

Download Vagrant boxes

  • Instead of downloading a large DVD image, we can download a small vagrant box.
  • We can manually download a new box using the vagrant box add command.
  • We only need to do this once for each vagrant box (e.g. one time for Oracle Linux 7 and one time for Oracle Linux 8).
  • This download process would also happen automatically if required, when you reference a new box in a Vagrantfile

In a DOS command prompt…

vagrant box add --provider virtualbox https://oracle.github.io/vagrant-projects/boxes/oraclelinux/7.json
vagrant box add --provider virtualbox https://oracle.github.io/vagrant-projects/boxes/oraclelinux/8.json

Some vagrant addons

  1. allows us to resize disks (optional)

In a DOS command prompt…

vagrant plugin install vagrant-disksize
  1. ensure the virtualbox guest additions is updated, required to ensure that the guest additions are automatically updated for all new vagrant boxes

In a DOS command prompt…

vagrant plugin install vagrant-vbguest
  1. Automatically update the /etc/hosts

In a DOS command prompt…

vagrant plugin install vagrant-hostsupdater

Create the initial vagrantfile

To create the virtual machine, we first of all create a new directory, change to it and create the initial “vagrantfile”

In a DOS command prompt…

mkdir D:\vagrant\vol7db19
cd /D D:\vagrant\vol7db19
vagrant init

Start the VM

edit the vagrantfile (see Tim Hall’s website above) and when ready with our configuration, we can install, create and start the VM with the following command…

In a DOS command prompt…

vagrant up

Changing the vagrantfile

if you change the vagrantfile, destroy and recreate your virtual machine

In a DOS command prompt…

vagrant destroy -f
vagrant up

accessing the VM

  1. use the command “vagrant ssh” to access the VM per shh in your DOS command prompt
  2. or connect with ssh to 127.0.0.1, port 2222 with your favourite tool

Removing Vagrant boxes

  • We can remove any old boxes we are no longer using, with the vagrant box remove command.
  • These boxes will be automatically downloaded again if required.
  • It is best not to remove them, if still used regularly, as it takes a few minutes to download them

In a DOS command prompt…

vagrant box remove oraclelinux/7
vagrant box remove oraclelinux/8

1.1.2. What are we going to do?

With one command, the following will happen…​

  • An Oracle Linux VM will be created.

1.2.3.1. What happens when I start vagrant?

  1. Using the vagrantfile, an Oracle Linux VM is installed (2x CPU, 4096MB RAM, 150GB HDD). IP = 192.168.56.161

  2. A mount point /vagrant is available in the Oracle Linux VM. This is a shared folder from your Windows machine.

  3. Your ssh key is used to connect to the VM in a secure way

  4. docker is installed in the Oracle Linux VM

  5. docker-compose is installed in the Oracle Linux VM

  6. The ansible-oracle repository is cloned to the Oracle Linux VM

  7. A docker container "Ansible Container" is built with docker-compose. This runs in the Oracle Linux VM

  8. No Oracle database is yet installed. See below

1. Intro

This guide will show you how to get Ansible-Oracle up and running with a local installation (as opposed to a container or Vagrant setup).

It is assumed that the server is airgapped and doesn’t have Internet access and therefore it’s demonstrated how to install all necessary binaries manually.

Note
 This guide aims at developers who want to test different setups with different dependencies. To enable you to run the Ansible-Oracle environment independently of other versions of Ansible, Python and Galaxy modules, everything will be encapsulated within a Python Virtual Environment (venv). If you prefer to install everything globally, you’ll find info on how to do so below.

The steps in this guide were tested with OL9.5, Python 3.9, Ansible 2.14 and Ansible-Oracle 4.11.1.

2.6 - Installation & Patching Settings for the Inventory

1. Introduction

This guide explains the variables used in the inventory to configure RDBMS installation and patching. Usually, both are done at the same time, because for most scenarios you wouldn’t install just the base release of the Oracle RDBMS.

Not described are the details of patch provisioning, e. g., how to obtain the patch files and how to find and enter patch IDs in the inventory.

2. Typical Scenarios

Let’s look at some typical setups concerning where the Oracle software and patch binaries are placed and how they should be processed:

  1. The binaries are stored locally on the Ansible control node. From there they are copied over to the target, where they get unpacked and installed.

  2. The binaries are stored in compressed form on NFS and should be copied over to the target, where they get unpacked and installed.

  3. The binaries are stored in compressed form on NFS. The NFS share will be mounted on the target host and the files will be unpacked from there to /tmp on the target host, then installed from the temp directory.

  4. The binaries are stored uncompressed on NFS. The NFS share will be mounted on the target host and the files will be installed from there.

Here is how the inventory variables interact and what to set for each scenario.

Note that the opatch part of the db home to be patched doesn’t need a path to be set when the required NFS path structure is as above. The patchid is enough in this case. Here’s an example of the settings for the DBRU 19.25:

apply_patches_db: true
db_homes_config:
  db1925-si-ee:
    version: 19.3.0.0
    oracle_home: /u01/app/oracle/product/19/dbhome_1
    edition: EE
    opatch_minversion: 12.2.0.1.44
    state: present
    opatchauto: []
    opatch:
      - patchid: 36912597
        # Database Release Update 19.25.0.0.240716
        patchversion: 19.25.0.0.241015
        stop_processes: true
        state: present
      - patchid: 36878697
        # Oracle JavaVM Component Release Update (OJVM RU) 19.25.0.0.241015
        stop_processes: true
        state: present

However, you could set a path attribute for each patchid if you want to deviate from the standard setups. This might be necessary when you use a "combo patch" instead of separate patch archives for DBRU, OJVM RU et al.

6. Key Behavioral Differences: Installation vs. Patching

For installation, setting oracle_sw_copy: false + oracle_sw_unpack: true (Scenario 3) causes the installer to read the archive from oracle_stage_remote (NFS) and extract directly to oracle_home_db.

For patching, the unpack block unconditionally requires oracle_sw_copy: true. When oracle_sw_copy: false, no copy or unpack step runs at all — the patch must already be extracted on the NFS share at oracle_patch_stage_remote/<version>/<patchid>/. Scenarios 3 and 4 are therefore identical from a patching perspective.

Important

The role autoupgrade uses Oracle AutoUpgrade (autoupgrade.jar) for:

  • Installation of autoupgrade.jar on the database servers or on the Ansible controller

  • Download of the latest autoupgrade.jar from Oracle into the software repository

  • Management of the AutoUpgrade keystore with the My Oracle Support credentials

  • Download of patches from My Oracle Support (-patch -mode download)

  • Java on the host executing AutoUpgrade

2. Proxy

The download of autoupgrade.jar (get_url) and AutoUpgrade itself (keystore, download of patches) use the proxy variables of ansible-oracle: http_proxy, https_proxy and no_proxy. AutoUpgrade reads the lowercase environment variable https_proxy.

AutoUpgrade needs access to updates.oracle.com, login-ext.identity.oraclecloud.com and aru-akam.oracle.com. Use DNS names in the proxy/firewall configuration - the addresses are part of a CDN.

Java disables Basic authentication for HTTPS tunneling through a proxy by default. With proxy credentials the role adds -Djdk.http.auth.tunneling.disabledSchemes= to the Java options of AutoUpgrade.

8.4.3. Hints for gold images

  • Time: When the Oracle Update Advisor service has to create the gold image, this can take a few hours. AutoUpgrade waits for the gold image. Request gold images well in advance of the maintenance window.
    One-off patches (ALL) reduce the chance that a suitable gold image is already cached.

  • Individual images: The gold images are built by Oracle on request of AutoUpgrade. Their content depends on the requirements sent by AutoUpgrade (e.g. release update, patch list, one-off patches, gold_image YES or ALL). Each download can therefore result in an individual image.

  • Filename: Because each gold image can be individual, AutoUpgrade generates a new filename for each download. The filename contains a timestamp (db_goldimage_<release>_<update>_<timestamp>.zip). It cannot be changed.

  • Repeated downloads: Because of the new filename, AutoUpgrade cannot detect an existing gold image. It downloads the gold image again in each execution with AUTO, YES or ALL.
    Recommendation: autoupgrade_download_gold_image: "NO" in the inventory and a gold image only in dedicated runs.

  • Disk space: Old gold images are not removed by AutoUpgrade or the role. Remove them manually from autoupgrade_download_dir.

  • Usage: AutoUpgrade uses gold images from download_folder for the creation of new Oracle homes (create_home mode). This is not implemented in the role yet.
    db_homes_config supports golden images (imagename, filesource) for the installation with oraswdb_install. Whether a gold image from AutoUpgrade can be used there, is not tested.

  • Information: patches_info.json in autoupgrade_download_dir lists the downloaded gold images with release update and included patches.

Disable the download of gold images for all sections
autoupgrade_download_gold_image: "NO"
Note
 Quote "NO" in YAML. An unquoted NO is a boolean - the role converts true/false into YES/NO anyway.

8.5. Repeated downloads

AutoUpgrade does not download patches again, when they already exist in autoupgrade_download_dir. The output shows LOCATED for existing files and VALIDATED for downloaded files. The task is reported as changed, when at least one file was downloaded.

AutoUpgrade writes patches_info.json into autoupgrade_download_dir.

9. Known limitations

  • Patching databases with AutoUpgrade is not implemented yet.

  • The download on the Ansible controller uses the variables of the first host in the play (see above).

  • An explicit entry in autoupgrade_download_patches and the derived entry from db_homes_installed / oracle_sw_patches for the same release create two sections in the config file. Set autoupgrade_download_use_oracle_sw_patches: false, when only autoupgrade_download_patches should be used.

  • The filename of a downloaded gold image cannot be changed. Gold images are downloaded again in each execution.

2.9 - Upgrade of PDBs with AutoUpgrade (Unplug/Plug)

Important

1. End state in oracle_pdbs

oracle_pdbs always defines the end state of a PDB. For the upgrade this is the PDB in the target CDB of the new release:

  • cdb: the target CDB

  • home: the target ORACLE_HOME

The source of the PDB is defined with the attribute autoupgrade of the PDB. It is used by the role autoupgrade only.

Warning

Do not execute playbook manage_db between the change of oracle_pdbs and the upgrade!

As soon as a PDB in oracle_pdbs points to the target CDB, oradb_manage_pdb (playbook manage_db) tries to reach this end state. It does not know AutoUpgrade and creates a new, empty PDB in the target CDB instead of migrating the existing PDB.

  • The analyze phase detects this situation (PDB exists in source and target CDB, state conflict) and fails. The empty PDB must be dropped manually before the upgrade.

  • Execute manage_db again only after a successful upgrade (autoupgrade_upgrade.yml).

  • Prepare everything, which needs manage_db (e.g. the target CDB), before oracle_pdbs is changed.

3. Requirements

  • Source and target ORACLE_HOME are installed (db_homes_config, db_homes_installed, playbook swdb)

  • The source CDB is running from the source ORACLE_HOME

  • The target CDB exists and is running from the target ORACLE_HOME. It is created with playbook manage_db before the PDBs are changed in oracle_pdbs. 26ai supports Container Databases only.

  • AutoUpgrade (autoupgrade.jar) in the software repository. It is installed on the database server by the task files.

  • Java: the JDK of the target ORACLE_HOME is used, when autoupgrade_java_home is empty

  • AutoUpgrade is executed on the database server as oracle_user. The playbooks set autoupgrade_run_local: false. The task files fail with autoupgrade_run_local: true.

  • Upgrade paths, minimum Release Updates, character sets, components etc. follow the rules of Oracle for AutoUpgrade

5.1. NOCOPY (default)

oracle_pdbs:
  - cdb: DB1
    home: db26-si-ee
    pdb_name: ORCLPDB1
    state: present
    autoupgrade:
      source_cdb: DB2

  • Fastest way. Recommended for big PDBs, when a backup of the PDB exists.

  • After the upgrade the datafiles of the PDB in the target CDB are still in the directory of the source CDB, e.g. /u01/app/oracle/oradata/DB2/<GUID of the PDB>/datafile/. They can be moved later online with alter database move datafile in the target CDB.

  • Recommended for OMF and ASM (AutoUpgrade: "For ASM/OMF, use: file_name_convert=none").

  • The target CDB needs db_create_file_dest (or pdb_file_name_convert). Set it with init_parameters of the target CDB in oracle_databases.

  • The datafiles are created in the directory of the target CDB, e.g. oradata/DB1/<GUID>/datafile.

  • Needs disk space and time for a complete copy of the PDB. The downtime of the PDB includes the copy.

5.3. Copy with path conversion

oracle_pdbs:
  - cdb: DB1
    home: db26-si-ee
    pdb_name: ORCLPDB1
    state: present
    autoupgrade:
      source_cdb: DB2
      copy_option: "file_name_convert=('/u01/app/oracle/oradata/DB2/', '/u01/app/oracle/oradata/DB1/')"

  • More than one pair is possible: file_name_convert=('/a/', '/x/', '/b/', '/y/').

  • The target directories must exist and must be writable for oracle_user.

  • Quote the value in YAML because of the brackets and quotes.

6. Process overview

  1. Preparation with manage_db (no downtime) - oracle_pdbs still points to the source CDB

    1. Install the target ORACLE_HOME with playbook swdb (db_homes_installed)

    2. Add the target CDB to oracle_databases and create it with playbook manage_db

  2. Change the inventory to the end state

    1. cdb and home of the PDBs in oracle_pdbs: target CDB and target ORACLE_HOME

    2. Add the attribute autoupgrade with source_cdb to the PDBs

    3. From now on: no manage_db until the upgrade is done!

  3. Analyze phase (no downtime): autoupgrade_upgrade_analyze.yml

    1. Install autoupgrade.jar on the database server

    2. Read the PDBs of the source and the target CDB (v$pdbs)

    3. AutoUpgrade analyze for the PDBs in the source CDB

    4. Evaluate the prechecks. Fail on errors without automatic fixup.

  4. Fix the reported problems and repeat the analyze phase until it is successful

  5. Fixups phase (no downtime, optional): autoupgrade_upgrade_fixups.yml

    1. AutoUpgrade fixups for the PDBs in the source CDB, e.g. some days before the deploy

    2. Evaluate the prechecks like the analyze phase

  6. Deploy phase (downtime of the PDBs): autoupgrade_upgrade.yml

    1. Analyze phase (again)

    2. AutoUpgrade deploy: prechecks, fixups, unplug, plug, upgrade, postupgrade

    3. Check that the PDBs are open READ WRITE in the target CDB

  7. Post tasks

    1. Execute playbook manage_db - the PDBs are in their end state now

    2. Remove the attribute autoupgrade from oracle_pdbs (optional - upgraded PDBs are skipped)

    3. Remove the source CDB, when it is not needed anymore (state: absent in oracle_databases)

8. Fixups phase

ansible-playbook -i inventory/ -e hostgroup=dbservers playbooks/autoupgrade_upgrade_fixups.yml

The fixups phase is the analyze phase with AutoUpgrade in mode fixups (upgrade_fixups.yml includes upgrade_analyze.yml):

  • Same checks of the source and the target CDB and the same states of the PDBs

  • AutoUpgrade executes the prechecks and applies the fixups (e.g. dictionary statistics, purge recyclebin) in the source CDB/PDBs. The PDBs are changed, but stay in the source CDB.

  • Same evaluation of the prechecks, logfiles and reports as the analyze phase. It fails on errors without automatic fixup.

The fixups phase is optional. Execute it some time before the deploy to shorten the downtime. Without it, AutoUpgrade applies the fixups during the deploy.

9. Deploy phase

ansible-playbook -i inventory/ -e hostgroup=dbservers playbooks/autoupgrade_upgrade.yml

# one PDB only
ansible-playbook -i inventory/ -e hostgroup=dbservers -e '{"autoupgrade_upgrade_pdbs": ["ORCLPDB1"]}' \
  playbooks/autoupgrade_upgrade.yml

upgrade_deploy.yml:

  1. executes the analyze phase (upgrade_analyze.yml)

  2. executes autoupgrade.jar -config upgrade_<job>.cfg -mode deploy -noconsole for each job in state analyzed (async: autoupgrade_upgrade_timeout, poll: autoupgrade_upgrade_poll)

  3. checks that all PDBs of the job are open READ WRITE in the target CDB and are gone from the source CDB

The jobs are executed one after the other.

Follow the progress on the database server
tail -f /u01/app/oracle/cfgtoollogs/autoupgrade/DB2_DB1/cfgtoollogs/upgrade/auto/autoupgrade.log

9.1. Repeated execution

  • PDBs in the target CDB are skipped (state upgraded). The playbook can be executed again without changes.

  • An interrupted or failed deploy is resumed by the next execution of autoupgrade_upgrade.yml, see Recovery data of AutoUpgrade.

9.2. Recovery data of AutoUpgrade

AutoUpgrade keeps recovery data after each deploy in autoupgrade_log_dir/<job>/cfgtoollogs/upgrade/auto (config_files/upgradeJobs.bin, state.txt) - for a finished deploy as well as for an interrupted or failed one. As long as the recovery data exists, AutoUpgrade refuses analyze, fixups and a new deploy with the same config file:

There is an unfinished execution of a deploy mode. Run the AutoUpgrade in deploy mode to resume from failure point

  • See Datafiles: NOCOPY or copy: a fallback into the source CDB is possible with a copy of the datafiles only.

  • restoration: true / autoupgrade_upgrade_restoration: true: AutoUpgrade creates a Guaranteed Restore Point (upg1.restoration=yes). Requires a Fast Recovery Area and Enterprise Edition. Check the Oracle documentation, how the restore point is used for an Unplug/Plug upgrade.

The fallback is not implemented in the role.

Important
 Take a backup before the upgrade.

10. After the upgrade

oracle_pdbs describes the end state already. Nothing has to be changed for the PDBs.

  • Execute playbook manage_db. It manages the PDBs in the target CDB now (tablespaces, users, services, …​).

  • The attribute autoupgrade can be removed from oracle_pdbs. Upgraded PDBs are skipped anyway.

  • Services, tnsnames.ora entries and wallets, which point to the source CDB, must be changed to the target CDB.

  • Remove the source CDB, when it is not needed anymore (state: absent in oracle_databases), and the source ORACLE_HOME (db_homes_installed).

12. Known limitations

  • Unplug/Plug upgrade of PDBs into an existing CDB on the same host only. Upgrade of a whole CDB, non-CDB to PDB conversion, RAC, Oracle Restart and Data Guard are not supported.

  • The jobs are executed one after the other. AutoUpgrade can execute jobs in parallel - not used by the role.

  • The fallback is not implemented in the role.

  • manage_db must not be executed between the change of oracle_pdbs and the upgrade (see warning above).

  • The evaluation of the prechecks depends on *_checklist.json, which is not documented by Oracle.

  • Patching of databases with AutoUpgrade (-patch) is not implemented.

2.10 - Out-of-Place Patching - Switch ORACLE_HOME

Important
 Out-of-Place Patching is supported for Single Instance primary databases without Grid Infrastructure/Oracle Restart only.
The guide describes the concept, all dependencies and the gaps in the current implementation.

Out-of-Place Patching switches a database from its current ORACLE_HOME to another, already installed and patched ORACLE_HOME. The installation and patching of the new ORACLE_HOME is not part of Out-of-Place Patching. It is done before with other roles (oraswdb_install, oraswdb_manage_patches or from a Golden Image).

Advantages compared to In-Place Patching with opatch apply:

  • The new ORACLE_HOME is installed and patched before the switch without downtime, because no database is running from it.

  • The downtime is reduced to a restart of the database and datapatch.

  • Fallback is easy: the old ORACLE_HOME is still available.

Note
 A Golden Image is recommended, but not required.
The new ORACLE_HOME can also be installed and patched with ansible-oracle on the database server. The switch of the database is independent from the way the new ORACLE_HOME was created. See Preparation of the new ORACLE_HOME.

1. Requirements

  • Oracle Database 19c or newer

  • Read-Only Oracle Homes (readonly_home: true) are recommended, but not required

    • Configuration files like SPFile and password file are not part of the ORACLE_HOME and are shared between all Read-Only `ORACLE_HOME`s.

    • The switch copies SPFile, PFile and password file, when the location differs between old and new ORACLE_HOME (e.g. switch from a Read-Write into a Read-Only ORACLE_HOME).

    • readonly_home must not be changed for an installed ORACLE_HOME.

  • Each Read-Only ORACLE_HOME needs 2 attributes in db_homes_config:

    db_homes_config:
  db1932-si-ee:
    readonly_home: true
    oracle_home_name: db1932siee

  • oracle_home_name is mandatory:

    • It cannot be derived from the key in db_homes_config. Oracle allows only characters, numbers and _ in the name of an ORACLE_HOME in the Oracle Inventory. YAML keys are much less restrictive (e.g. db1932-si-ee is a valid key, but not a valid oracle_home_name).

    • It must be unique over all ORACLE_HOME`s on a server. It defines the `ORACLE_BASE_HOME ($ORACLE_BASE/homes/<oracle_home_name>), which must not be shared between the old and the new ORACLE_HOME.

  • Enough disk space for at least 2 `ORACLE_HOME`s at the same time

    2. Create the network configuration in the new ORACLE_BASE_HOME

  3. Post tasks

    2. Remove the old ORACLE_HOME after a successful test period

  • datapatch is mandatory after the start from the new ORACLE_HOME.

  • datapatch must be executed for the CDB and all PDBs.

The upgrade is an Unplug/Plug upgrade of PDBs into a CDB of the new release. oracle_pdbs defines the end state: cdb and home are the target CDB and target ORACLE_HOME. The source is defined with the attribute autoupgrade of the PDB:

Attribute Description
source_cdb mandatory: oracle_db_name of the source CDB
source_home optional: key in db_homes_config of the source ORACLE_HOME. Default: home of source_cdb in oracle_databases
source_sid optional: SID of the source CDB. Default: from source_cdb in oracle_databases, otherwise source_cdb
source_pdb_name optional: name of the PDB in the source CDB. Default: pdb_name
copy_option optional: upg1.target_pdb_copy_option.<pdb>, e.g. file_name_convert=NONE. Default: datafiles are reused (no copy)
restoration optional: true/false - default autoupgrade_upgrade_restoration
parameters optional: dict with additional AutoUpgrade parameters (upg1.<key>=<value>). Overrides autoupgrade_upgrade_parameters.

All PDBs with the same source_cdb and cdb are upgraded in one AutoUpgrade job. restoration and parameters must be identical for these PDBs.

Everything about the development of ansible-oracle.

4.1 - How to develop

1. How to develop in ansible-oracle?

Important
 This is an example how most of the development in ansible-oracle is done.
A Pull-Request is only accepted, when github-Actions are valid.

1.1. Create Fork on github and contribute to the project

github has some great documentation with details about creating a fork and branch to contribute to ansible-oracle.

Important
 The github-Actions will automatically start, when the branchname starts with pr or in each Pull-Request.
Please use a branch with 'pr'--prefix, when ansible-lint should be checked for each commit.

1.2. Development environment

You need an editor or IDE of your own choice and Bash as CLI. The tools for development (ansible-lint, ansible-navigator, ansible-doctor, pre-commit, …​) can be provided in two ways:

Option 1: nix-shell Option 2: local Ansible-Controller

Setup

Install Nix once, then nix-shell in the repository

Create and maintain venvs and tools manually

Tools

All tools and venvs are provided automatically

Each tool is installed by yourself

Recommended for

All developers

Developers with an existing Ansible-Controller or experience with Docker
Tip
 nix-shell is the recommended way for developing in ansible-oracle.

1.2.1.1. What is nix-shell?

Nix is a package manager for Linux and macOS, which works independent of the package manager of the OS (dnf, apt, …​). All packages are installed in /nix/store, each version in its own directory. Different versions of a tool can be installed in parallel without conflicts, the OS installation is not changed.

nix-shell starts a new shell with the packages from shell.nix in the repository. The tools are only available inside this shell, exit returns to the normal shell without any change in the OS. Packages are downloaded once and reused in all later sessions.

The shell.nix of ansible-oracle provides:

  • Tools from Nix: python313, shellcheck, go-task (task), jq, yq, gh (GitHub CLI), renovate, tig, ncdu and wslu for WSL2.

    Note
    		 gh is only needed for creating releases (task release:*) and for running renovate against a fork. This is only relevant for a few maintainers. For normal development and Pull-Requests gh is not needed and no login with gh auth login is required.

  • Python venvs in .venv/ of the repository, which are created automatically from tools/dev/requirements_*.txt at the first start:

    venv Usage

    .venv/ansible-oracle

    ansible-lint, ansible-navigator, molecule, pre-commit - activated in the shell

    .venv/ansible-doctor

    ansible-doctor (has conflicts with ansible-lint in the same venv)

    .venv/antsibull

    antsibull-changelog for changelog fragments and releases

    .venv/ansible-2.16

    tests with ansible-core 2.16

    .venv/ansible-2.19

    tests with ansible-core 2.19
1.2.1.2. Why nix-shell instead of containers?

Containers (see docker/) are an alternative, but they need much more effort in daily work:

  • No image build, no container runtime: There is no Dockerfile to maintain and no daemon to start. nix-shell works on every Linux, WSL2 and macOS with Nix installed.

  • Work directly in your repository: Editor, IDE and git work on the files as usual. There are no volume mounts and no problems with file owners or UIDs between container and host.

  • Your credentials are available: SSH agent and keys and the git configuration of your user are used directly, for maintainers also the login of gh. A container needs extra mounts for all of them.

  • pre-commit works as on GitHub: The hooks of pre-commit use the Python and tools from nix-shell. E.g. the ansible-lint hook fails outside of nix-shell with the Python of an older OS.

  • Same tools for all developers: Everybody uses the same tools and pip requirements from the repository. No manual installation of shellcheck, gh, jq, task or the venvs is needed.

  • All tasks work out of the box: task for molecule, renovate and releases (task release:pr, …​) needs exactly the tools from nix-shell.

  • Nothing is left in your OS: The tools are removed from PATH when the shell is left. The venvs are inside the repository in .venv/ and are not part of git.

3.2. Working with antsibull-changelog

Changelogs for Collections: https://github.com/ansible-community/antsibull-changelog/blob/main/docs/changelogs.rst#releasing-a-new-version-of-a-collection

3.3. Add PR references to fragments

Each entry in a fragment should end with a reference to its Pull-Request, e.g. (oravirt#599). tools/release/fix_fragments.py adds missing references to all fragments in changelogs/fragments.

The Pull-Request is determined from the commits of the fragment file via the GitHub API, newest commit first. A merged Pull-Request of any of these commits wins over an open one. The open Release-Pull-Request is only used for fragments, which are not part of a merged Pull-Request. The reference is appended to every entry that does not end with it, even if the entry already references an issue.

# show what would be changed
tools/release/fix_fragments.py --dry-run

# update the fragments
tools/release/fix_fragments.py

Single fragments can be checked with -f / --fragment, e.g. by a developer after the Pull-Request for a new fragment has been created. The parameter accepts a path or a filename from changelogs/fragments and can be repeated. With --dry-run the script returns exit code 1 if the fragment needs to be updated.

# check a single fragment
tools/release/fix_fragments.py --dry-run -f blanks-in-gi-responsefile.yml

# update a single fragment
tools/release/fix_fragments.py -f changelogs/fragments/blanks-in-gi-responsefile.yml
Note
 The Pull-Request must exist on GitHub, otherwise the fragment is reported as no pull request found.

Fragments without a Pull-Request and entries that cannot be updated automatically (e.g. broken quoting) are reported and must be fixed manually. The script returns exit code 1 in this case.

Without --fragment all fragments in changelogs/fragments are processed.

Note
 Without a token the GitHub API allows only 60 requests per hour. The token is taken from GITHUB_TOKEN or GH_TOKEN. Without these variables the token stored by gh is used, when all fragments are processed (gh auth token or ~/.config/gh/hosts.yml of the active account). An invalid token is ignored with a warning.

This must be done before antsibull-changelog release, because the release removes the fragments.

3.4. Collection version in requirements.yml

The examples in example/*/ansible/requirements.yml must reference the collection version from galaxy.yml. The same is needed for the template tools/release/requirements.yml. tools/release/galaxy_version.sh checks or sets the version in all these files.

# check the versions
tools/release/galaxy_version.sh check

# set the version from galaxy.yml
tools/release/galaxy_version.sh fix

check returns exit code 1 if a file does not use the version from galaxy.yml. fix changes only the version of the collection entry, comments in the files are kept.

The script is also available as task example:check and task example:fix from the repository root.

3.5. Creating new releases

tools/release/build_release.sh executes the whole release process in two steps:

-m pr

Create the Release-Pull-Request with changelog.

-m release

Create the tag and a draft release for the Release-Pull-Request.

-m galaxy

Sync master of your fork with master of the upstream repository.

-m docs

Update the website, without creating a release.

Note
 The whole release process should be done with a dedicated Pull-Request.

Requirements:

  • The release branch is named pr/<major>.<minor>.<patch>, e.g. pr/4.16.0.

  • origin is your fork on GitHub.

  • gh is logged in (gh auth status), jq and curl are installed and .venv/antsibull exists. gh, jq and the venv are provided by nix-shell.

  • The script is executed in nix-shell, because the pre-commit hooks of the version commit need it.

nix-shell
git switch -c pr/4.16.0
tools/release/build_release.sh -m pr

3.5.1. Release-Pull-Request (-m pr)

The script executes the following steps:

  1. Read the version from the branch name (pr/4.16.0 → 4.16.0) and set it in galaxy.yml.

  2. Set the version in all requirements.yml with tools/release/galaxy_version.sh fix.

  3. Commit galaxy.yml and all requirements.yml as Release <version>. This is the initial commit for the Pull-Request, GitHub refuses a Pull-Request without commits. Other changes in the working tree and the index are not part of this commit. The step is skipped, when the version is already committed.

  4. Push the branch to origin.

  5. Create the Pull-Request Release <version> in oravirt/ansible-oracle. An existing open Pull-Request of the branch is used.

  6. Add the PR references to the fragments with tools/release/fix_fragments.py. The script is aborted, when fragments cannot be updated.

  7. Create the changelog with .venv/antsibull/bin/antsibull-changelog release. antsibull-changelog reads the version from galaxy.yml and aborts, when the release already exists in CHANGELOG.rst. The fragments are removed.

  8. Replace the description of the Pull-Request with the release notes of the new version (Markdown, antsibull-changelog generate --only-latest).

The changes of fragments and changelog are not committed by the script. Review them, then commit and push them to the release branch.

3.5.2. Draft release (-m release)

tools/release/build_release.sh -m release

The script executes the following steps:

  1. Search the Pull-Request of the release branch from your fork, open or merged.

  2. Create the tag v<version> (e.g. v4.16.0) like the existing release tags. The tag points to the merge commit of the Pull-Request. When the Pull-Request is still open, the last commit of the Pull-Request is used.

  3. Push the tag to the git remote of the GitHub repository (e.g. upstream for oravirt/ansible-oracle). An existing tag is used, when it points to the same commit, otherwise the script is aborted.

  4. Create the draft release Release <version> with the description of the Pull-Request as text. The text of an existing draft release is updated, an already published release aborts the script.

  5. Update the website with tools/release/build_website.sh -m push, see website.adoc. The website is built from the local checkout of the release branch and published at once. This step is skipped for tests against a fork (-r other than oravirt/ansible-oracle).

The draft release must be published manually on GitHub.

Note
 The website step needs docker, rsync and task and committed sources in website/, doc/, roles/ and docker/hugo/. When it fails, fix the problem and run -m release again: the existing tag and draft release are reused.

3.5.3. Update the website (-m docs)

tools/release/build_release.sh -m docs

Builds and publishes the website with tools/release/build_website.sh -m push, like the last step of -m release. Use it to update the website without a release, e.g. after changes in doc/ or website/, or to repeat a failed website step of -m release. No release branch is needed, the website is built from the current local checkout. The step is skipped with -r other than oravirt/ansible-oracle.

For more options (commit only, Pull-Request in the website repository) use tools/release/build_website.sh directly, see website.adoc.

3.5.4. Sync fork (-m galaxy)

tools/release/build_release.sh -m galaxy

GitHub syncs the fork in the background. -m galaxy forces the sync of master in your fork with master of the upstream repository (gh repo sync), to take over a release merged in upstream at once. The fork is <gh user>/ansible-oracle, the user is taken from the login of gh. Afterwards the last commit of master in the fork is shown.

When the last commit of master in the fork is a release commit (Release <version>), the latest published release of the upstream repository is checked. Draft releases are ignored, so the release must be published before.

If the release points to this commit, the workflow Deploy Collection is started in the fork, which uploads the collection to Ansible Galaxy. The script waits for the workflow and shows the progress of the steps (gh run watch). When the workflow fails, the log of the failed steps is shown and the script returns exit code 1. The workflow is not started, when the version is already on Ansible Galaxy, so -m galaxy can be repeated safely.

The mode works only on GitHub with gh (and the API of Ansible Galaxy), nothing is changed locally and no release branch is needed. The sync is refused, when master of the fork contains own commits - no hard reset is done.

3.5.5. Tasks

The modes are also available as tasks from the repository root. Options are passed after --.

task release:pr        # -m pr
task release:draft     # -m release (incl. website)
task release:docs      # -m docs
task release:galaxy    # -m galaxy

The creation of the Release-Pull-Request can be tested against your fork:

task release:pr -- -i -r <github user>/ansible-oracle

The Pull-Request is then created in your fork instead of oravirt/ansible-oracle.

Warning
 fix_fragments.py searches the Pull-Requests of the fragments in your fork and not in upstream. The fragments are part of Pull-Requests in oravirt/ansible-oracle, so the results are wrong: fragments get the reference of the test Pull-Request in your fork (e.g. Rendanic#93) or are skipped with no pull request found. -i is needed, otherwise the script stops at the skipped fragments. Changelog and description of the test Pull-Request contain these wrong references, never use them for a real release. Revert all changes in the working tree after the test.

3.5.6. Options

-m pr|release|galaxy|docs

Mode of the script, see above.

-r <owner/repo>

GitHub repository for the Pull-Request, the release, the lookup of the fragment Pull-Requests and source of the fork sync (default: oravirt/ansible-oracle).

-i

Continue, when fragments cannot be updated by fix_fragments.py (only -m pr).

A test against your fork is possible with -i -r <your account>/ansible-oracle, or -m release -r <your account>/ansible-oracle. The fragments get the reference of the Release-Pull-Request in the fork or are skipped, because the Pull-Requests of the fragments are in oravirt/ansible-oracle. Important

4.1. Local checks

The local checks read the working tree and do not change anything. No GitHub setup is needed. renovate.json is read from the working tree, but it must be tracked by git.

task renovate:check     # pip modules and container images
task renovate:pip       # pip modules and pre-commit hooks
task renovate:docker    # container images only
task renovate:report    # show the result of the last run again
task renovate:validate  # validate renovate.json

Dependencies which are pinned intentionally (e.g. ansible-core or the molecule base images) are disabled with packageRules in renovate.json. They are shown as disabled in the report.

Tools which are used in requirements, in .pre-commit-config.yaml and in the github workflows (ansible-doctor, ansible-lint, antsibull-changelog) are grouped with groupName. An update changes all files in one branch, so the versions are always the same. The github workflow for ansible-doctor installs tools/dev/requirements_doctor.txt. The versions of github actions (e.g. ansible/ansible-lint) and of pip install <module>==<version> in the workflows are checked as well (only with task renovate:check).

The pre-commit hooks are looked up with GitHub tags, which needs a token. The local checks use the token from gh auth token, if gh is logged in.

4.2. Setup gh for renovate

Important
 The GitHub CLI gh is only needed for running renovate against your fork on GitHub (task renovate:fork).
The local checks work without it.

gh is part of shell.nix. Login once with your GitHub account:

gh auth login     # GitHub.com, HTTPS, login with a web browser
gh auth status

The token of gh needs the scope repo for pushing branches into your fork. This is part of the default scopes of gh auth login.

renovate reads the token from RENOVATE_TOKEN:

export RENOVATE_TOKEN=$(gh auth token)

4.3. Run renovate against your fork

renovate clones your fork from GitHub, creates a branch for each update and pushes it together with a Pull-Request into your fork. The configuration is taken from renovate.json in FORK_BASE of the fork, not from your working tree. renovate.json and tools/renovate/changelog_fragment.sh must be pushed into FORK_BASE before the first run. Without renovate.json renovate skips the fork (disabled-no-config).

FORK_REPO is the fork on GitHub, FORK_BASE the branch for the updates (default: master).

# show what would be done
task renovate:fork:dry-run FORK_REPO=<github user>/ansible-oracle

# create branches and Pull-Requests in the fork
task renovate:fork FORK_REPO=<github user>/ansible-oracle

The branches can be tested locally after git fetch origin.

The branches are named pr/renovate/<update>, so the github-Actions are started for each push. Each update adds a changelog fragment changelogs/fragments/renovate-<dependency>.yml in section minor_changes, created by tools/renovate/changelog_fragment.sh. The PR reference is added later with tools/release/fix_fragments.py.

Note
 renovate keeps the clones and its cache in ~/.cache/renovate. The clone is reset by each run, do not use it as working copy.

2. Where is the content?

The pages of the documentation are not copied into website/. hugo reads them directly from the repository:

Source Page

doc/.adoc, doc/guides/.adoc, doc/*.md

Guides, features and development

roles/*/README.md

One page per role (generated by ansible-doctor)

website/content/

Start page, About and the introduction of each section (_index.md)

website/hugo.yaml mounts doc/ and roles/ below assets/. The content adapter website/content/docs/_content.gotmpl creates the pages from them:

  • The first heading of a file is used as the page title, unless a title is set in $settings of the content adapter.

  • Relative links between the documents (AsciiDoc link: macro or Markdown link to a .adoc or .md file) are rewritten to the pages of the website. Links to files without a page point to GitHub.

  • The "Edit this page" link points to the source file below doc/ or roles/.

  • "Last modified" shows the last commit of the source file. scripts/gitinfo.py writes it to website/data/gitinfo.json before each build (hugo would show the commit of the content adapter instead).

  • A new file in doc/guides/ appears automatically. New files in other directories need a rule in $rules of the content adapter.

Important
 Do not use include:: in files below doc/. hugo passes the content to asciidoctor by stdin and GitHub does not render includes either. Use a link instead.

website/Taskfile.yml contains the commands for building and testing the page. task is part of the nix-shell of ansible-oracle.

cd ansible-oracle/website
task                # list all tasks
task serve          # live server on http://localhost:1313
task build          # build the page into public/
task test           # build + check internal links
task test:a11y      # build + accessibility check (WCAG 2 AA) of all pages
task publish        # build + commit in the clone of the website repository
task publish:push   # build + commit + push => GitHub Pages publishes the website
task publish:pr     # build + commit + pull request in the website repository

The tasks can be started from the root of the repository with prefix website:, e.g. task website:test.

4. Publishing

The website is published with GitHub Pages from the directory docs/ in the branch main of Rendanic/ansible-oracle-website.

The publish tasks call tools/release/build_website.sh:

  • The sources in website/, doc/, roles/ and docker/hugo/ must be committed.

  • The legal notice must be published (no draft: true).

  • The website repository is cloned to ~/.cache/ansible-oracle-website with gh.

  • docs/ is replaced by the new build, CNAME is kept and .nojekyll is added (GitHub Pages ignores directories with a leading _ like _print/ without it).

Options of the script are passed after --, e.g. task publish — -a for an additional accessibility check or task publish — -f to ignore uncommitted changes and a missing legal notice (for tests only).

Podman is used with task build COMPOSE=podman-compose COMPOSE_USER=root.

The checks run in containers:

  • check:links uses lychee for all links in public/.

  • check:a11y uses pa11y-ci with the runners axe and HTML_CodeSniffer for all pages in sitemap.xml. The settings are in website/.pa11yci.json. The axe rule color-contrast is ignored: axe cannot determine the background below the fixed navbar and sidebar and reports hundreds of false positives. The contrast is still checked by HTML_CodeSniffer.

5. Colors and contrast

The whole site uses one polarity: dark text on a light background. Docsy’s dark navbar, cover blocks and footer are replaced in

  • website/layouts/partials/navbar.html (copy of Docsy with data-bs-theme="light")

  • website/assets/scss/_styles_project.scss (navbar, footer, buttons, links and Prism token colors)

All colors have a contrast ratio of at least 4.5:1 (WCAG 2 AA). Use blocks/lead or blocks/section with color="white" on new pages, not blocks/cover. Code blocks are highlighted by Prism (light theme), Chroma is disabled for Markdown code fences in hugo.yaml.

The image of the hugo container is tagged with the tag of the base image, e.g. rendanic/hugo:0.169.0-ext-ubuntu. A new version in the Dockerfile builds a new image automatically with the next task build.

Steps for an update of Docsy:

  1. Read the release notes of Docsy (minimum version of hugo, breaking changes).

  2. Update website/go.mod and website/go.sum.

  3. task docsy:diff shows the differences between the copied templates in website/layouts/ and the new Docsy version. Apply the changes of Docsy to the copies.

  4. Check website/assets/scss/_styles_project.scss: it uses the Docsy classes .td-navbar, .td-footer, .td-box and .td-content.

  5. task test:all and a look at the start page, a guide and a role page.

9. hugo with Podman

9.1. hugo live server

The default user inside the container is hugo with a different uid then the nonroot user of the podman Container.
This results in a permission denied when the uid of nonroot podman user is different then the uid of hugo inside the container while reading volume data. Starting with --user=root starts all processes in the same namespace as the nonroot user which allows access to the volume data.

Start hugo server with Podman
cd ansible-oracle/docker/hugo
~/venv/podman/bin/podman-compose run --rm --user=root site -s /src/website server --bind 0.0.0.0
