Breaking Changes - Upgrade Guide

This guide lists all changes in ansible-oracle which require an action in your inventory, playbooks or environment when upgrading to a new major version.

How to use this guide:

  1. Find your current version and the target version.

  2. Read the overview table of every major version in between.

  3. Check the column Affected if against your inventory. Only the rows that match need an action.

Note
 The complete list of changes is in CHANGELOG.rst. This guide only covers the changes from the section Breaking Changes / Porting Guide and explains the required actions.

1. Version 5.0.0

1.4. Strict boolean conditionals with ansible-core 2.19

ansible-core 2.19 requires a real boolean as result of a conditional (when, failed_when, changed_when, until, assert: that). Older versions converted strings like "false" or "yes" silently. Now the task fails:

Conditional result (True) was derived from value of type 'str' at '...'. Conditionals must have a boolean result.

ansible-oracle 5.0.0 evaluates all boolean variables from the inventory with | bool. Strings like "true", "yes", "false" or extra-vars like -e oracle_sw_copy=false work as before.

Your own playbooks and roles are affected, when they use variables directly in conditionals:

# fails with ansible-core 2.19, when my_flag is a string ("true", "yes", -e my_flag=true)
when: my_flag

# works with all versions
when: my_flag | bool

The bool filter accepts true/false, yes/no, on/off, 1/0 (case-insensitive). Other values (e.g. "enabled" or an empty string) result in a deprecation warning and false. This will be an error in ansible-core 2.23.

Tip
 ANSIBLE_ALLOW_BROKEN_CONDITIONALS=true restores the old behavior temporarily. Use it only to find the affected conditionals, not as permanent solution.

1.5. Templating changes with ansible-core 2.19

ansible-core 2.19 has a new templating engine. The result of a template has a different type in some cases. ansible-oracle 5.0.0 is adapted, but templates in your inventory are used as they are.

Template ansible-core < 2.19 ansible-core 2.19

"{% if x %}True{% else %}False{% endif %}"

bool

string "True" / "False"

"{% if x %}{'key': 1}{% endif %}", "{% if x %}[1, 2]{% endif %}"

dict / list

string

"{% if x %}-flag{% endif %}" with x false (empty result)

empty string ""

None

"{{ 1521 }}"

string "1521"

int 1521

Examples of failing expressions with ansible-core 2.19:

my_flag: "{% if foo %}True{% else %}False{% endif %}"
my_param: "{% if foo %}-flag{% endif %}"
my_port: "{{ 1521 }}"

# when: my_flag              -> fails: string instead of boolean
# when: my_param == ''       -> false, because the value is None
# "{{ my_param | length }}"  -> fails: None has no length
# "{{ 'host:' + my_port }}"  -> fails: string + int
# when: my_port == '1521'    -> false, because the value is an int

Recommendations:

  • Write expressions instead of text: my_flag: "{{ foo | bool }}" or my_flag: "{{ foo == 'x' }}".

  • Use YAML for lists and dictionaries instead of creating them as text.

  • Use | default('', true) when a template can be empty and a string is needed.

  • Use | int or | string for comparisons.

An empty template in environment: sets the environment variable to the text None, e.g. _JAVA_OPTIONS=None lets Java fail with Unrecognized option: None. Use "{{ my_value | default('', true) }}" for environment variables, which can be empty.

Embedding these values into other strings is not affected: "gridSetup.sh {{ my_param }}" renders an empty string for None in all versions.

1.6. Other ansible-core 2.19 changes for own playbooks and inventories

ansible-oracle 5.0.0 is checked for these changes. They are relevant for your own playbooks, inventories and ansible.cfg:

  • File modes must be quoted strings in inventories: mode: '0775' instead of mode: 775. An unquoted 775 is an integer and is passed through templates (for example mode: "{{ item.mode }}") as decimal 775, which is mode 1407. Before 2.19 the template converted the value to the string "775", which was interpreted as octal.

  • with_nested handles strings differently (not mentioned in the porting guide): an empty string "" is an empty list (the task is skipped completely), a templated string "{{ var }}" is split into single characters. Use lists: - [""] or - ["{{ var }}"].

  • A loop over an undefined list fails, although when is false, when delegate_to uses the loop variable (not mentioned in the porting guide). Use loop: "{{ my_list | default([]) }}".

  • Templates inside conditionals fail: that: swap >= {{ min_swap }} must be written as that: swap >= min_swap | int.

  • The ssh connection uses SSH_ASKPASS instead of sshpass for password authentication. Set password_mechanism = sshpass in section [ssh_connection] of ansible.cfg to keep the old behavior.

  • The bool filter warns for values other than true/false, yes/no, on/off, 1/0 (and None). This will be an error in ansible-core 2.23.

  • A timeout of become is an unreachable error. Use ignore_unreachable instead of ignore_errors.

  • The magic variable play_hosts is deprecated, use ansible_play_batch.

The complete list is in the ansible-core 2.19 Porting Guide.

1.7. Default of oracle_sw_copy and oracle_sw_unpack with install_from_nfs

The defaults of oracle_sw_copy and oracle_sw_unpack depend on install_from_nfs. Until 4.x the defaults were the strings "true" or "false". The string "false" is not empty and was evaluated as true in most conditionals. The documented behavior for install_from_nfs: true (no copy, no unpack) was therefore not active, unless both variables were set explicitly in the inventory.

As of 5.0.0 both defaults are real booleans.

no change

no change

Affected variables with changed default value: oracle_sw_copy, oracle_sw_unpack, oracle_stage_install, oracle_patch_install.

Keep the behavior of 4.x:

install_from_nfs: true
oracle_sw_copy: true
oracle_sw_unpack: true

1.8. Firewall enabled by default on RHEL/OL

Until 4.x the role orahost stopped and disabled firewalld on RHEL/OL by default (disable_firewall: true). As of 5.0.0 firewalld stays active and the role opens the ports of the Oracle listeners:

Variable 4.x 5.0.0

disable_firewall

true

false

firewall_open_listener_ports

- (not available)

true (new)

The change applies only to RHEL/OL target hosts with installed firewalld. SUSE is not changed.

What orahost does with the new defaults:

  1. Checks, if the permanent firewalld config allows the SSH connection of Ansible (service ssh, port and target of the zone). The play fails, when starting firewalld would block SSH. Rich rules and zones bound to sources are not evaluated by this check.

  2. Starts and enables firewalld.

  3. Opens the following TCP ports in the permanent and the running config:

    • all ports from address in oracle_listeners_config with a host (IPC addresses are ignored, listener_port is used for addresses without port),

    • all ports from the new variable oracle_extra_firewall_ports,

    • oracle_scan_port with oracle_install_option_gi: CRS_CONFIG.

Other ports are not opened automatically, e.g. EM Express (5500), ORDS/APEX or the Enterprise Manager agent. Add them to oracle_extra_firewall_ports:

oracle_extra_firewall_ports:
  - 5500  # EM Express
Warning
 Oracle RAC needs unrestricted network traffic on the private interconnect. Allow the interconnect in firewalld (for example with a trusted zone for the interconnect interfaces) or set disable_firewall: true on the cluster nodes.

1.9. Supported versions in db_homes_config

The role orasw_meta checks db_homes_config. It is a dependency of nearly all roles, so the check runs in nearly every playbook. As of 5.0.0 only Oracle 19c and 26ai are accepted as version:

Version Allowed version in db_homes_config

4.x

26.1.0.0, 21.3.0.0, 19.3.0.0, 18.3.0.0, 12.2.0.1, 12.1.0.2, 11.2.0.4, 11.2.0.3

5.0.0

26.1.0.0, 19.3.0.0

version is the base release of the ORACLE_HOME. Release Updates are not part of it, e.g. an ORACLE_HOME with 19.32 uses version: 19.3.0.0.

An ORACLE_HOME with another version stops the playbook with a failed assert, even when the ORACLE_HOME is not used by the playbook. Upgrade the databases to 19c or 26ai, e.g. with the role autoupgrade, and remove the old ORACLE_HOMEs from db_homes_config afterwards.

The assert can be disabled in emergency cases:

assert_db_homes_config: false
Warning
 assert_db_homes_config: false disables all checks of db_homes_config, not only the check of the version. Missing oracle_home, edition or opatch_minversion are no longer detected. ORACLE_HOMEs with other versions are not tested with ansible-oracle 5.x.

1.10. python-oracledb replaces cx_Oracle

python-oracledb (Python package oracledb) is the successor of cx_Oracle. All modules of ansible-oracle are migrated from cx_Oracle to python-oracledb. cx_Oracle is no longer used.

The new role pyoracledb installs python-oracledb with pip3 on the target hosts. The playbook os.yml executes pyoracledb instead of cxoracle.

1.11. oracle_profile, oracle_job, oracle_directory, oracle_grants and oracle_privs: names in double quotes are case sensitive

The modules oracle_profile, oracle_job, oracle_directory, oracle_grants and oracle_privs handle names like SQL (ANSI): a name in double quotes (") is case sensitive, a name without quotes is converted to uppercase. All other modules are not changed. The functions for this are in plugins/module_utils/oracle_identifier.py and can be used by more modules in the future. Such a change will be listed here.

Module Before Now

oracle_profile

The name was not quoted in the SQL statements, but compared case insensitive with DBA_PROFILES. A name in " was created case sensitive, but not found in the next run (ORA-02379).

A name in " is used case sensitive, e.g. name: '"Gestion/Monitorizacion"'. A name without " is used in uppercase and compared exactly with DBA_PROFILES.

oracle_job

A job_name with " failed with Invalid job name.

A part of job_name in " is case sensitive, e.g. job_name: 'SYSTEM."My_Job"'. convert_to_upper works as before for parts without ".

oracle_directory

The name was not quoted in the SQL statements and compared in uppercase with DBA_DIRECTORIES. A name in " was created case sensitive, but not found in the next run (ORA-00955).

A name in " is used case sensitive, e.g. directory_name: '"MyDir"'. "MyDir" and MYDIR are two different directories. A name without " is used in uppercase as before.

oracle_grants

The grantee (schema, role) was compared in uppercase, roles and objects in grants and object_privs were compared case insensitive, but not quoted in the SQL statements. A grantee or object in " was not found. Granting or revoking a privilege on an object with a lower or mixed case name failed (ORA-00942). With state: absent the names in grants had to be in lowercase. directory_privs needed sys.<directory>.

Grantee, roles in grants, owner and object in object_privs and the directory in directory_privs can be in " (case sensitive), e.g. schema: '"MyUser"', grants: ['"MyRole"'], object_privs: ['select:"MyOwner"."MyTable"']. Names without " are used in uppercase and compared exactly. state: absent compares in any case. An object without owner is in the current schema of the connection, sys. is optional for directories.

oracle_privs

Names with " failed with Invalid privilege, Invalid user/role or Invalid object. convert_to_upper was valid for all names in roles and objs. A role in privs was always converted to uppercase.

A name in " is case sensitive in roles, objs (owner and object, also with the wildcard %) and for a role in privs, e.g. roles: ['"MyUser"'], objs: ['"MyOwner".%'], privs: ['"MyRole"']. convert_to_upper works as before for names without ". No action needed, names without " are handled as before.

PDB names are not affected: Oracle stores them always in uppercase, oracle_pdb converts the name to uppercase as before.

For most inventories nothing changes, because names without " are stored in uppercase as before.

Important
 Check names which are enclosed in " by mistake, e.g. from a copied SQL statement. They are case sensitive now and refer to a different object than before, so the module creates a new profile or directory with the exact name, or grants a privilege on a different object or role. The roles of ansible-oracle do not use oracle_directory, so only own playbooks are affected for directories.

An existing profile with a name in lower or mixed case (created outside of ansible-oracle) was found before with a name in any case. Now the name must be given exactly in ", otherwise the module creates a new profile in uppercase.

The same applies to oracle_grants: a grant on an existing object or role with a lower or mixed case name, which was found before with a name in any case, must be given exactly in ". Otherwise the module tries to grant the privilege on the uppercase name (ORA-00942 or ORA-01919) and, with grants_mode: enforce, revokes the existing grant.

Find objects and roles with a name in lower or mixed case
select owner, object_name, object_type from dba_objects where object_name <> upper(object_name) or owner <> upper(owner);
select role from dba_roles where role <> upper(role);
Find profiles with a name in lower or mixed case
select distinct profile from dba_profiles where profile <> upper(profile);
Profile with a mixed case name in the inventory
oracle_pdbs:
  - cdb: DB1
    pdb_name: ORCLPDB
    profiles:
      # before: MyProfile was found case insensitive
      # - name: MyProfile
      - name: '"MyProfile"'
        state: present
        attributes:
          - {name: password_life_time, value: unlimited}

1.13. Quotas for users in oracle_user and oradb_manage_users

This is a new feature (#312), not a breaking change.

Note
 Without quotas no quota is removed or changed, the existing quotas of a user are kept. quotas_mode has no effect without quotas. A user with default_tablespace gets QUOTA UNLIMITED on this tablespace as before.

Quotas are only removed, if the inventory says so: with size: 0 for a tablespace in quotas, or with quotas_mode: enforce for all tablespaces not in quotas.

oracle_user and the users of oracle_databases / oracle_pdbs (role oradb_manage_users) have two new options:

  • quotas: list of tablespace and size. size is the number of bytes with an optional unit K, M, G, T, P, E or unlimited. size: 0 removes the quota on the tablespace.

  • quotas_mode: append (default) changes only the tablespaces in quotas, enforce removes all other quotas of the user.

Important
 With quotas, the default tablespace gets no automatic QUOTA UNLIMITED. Add the default tablespace to quotas, if the user needs a quota there. An existing quota on the default tablespace is kept with quotas_mode: append, but removed with quotas_mode: enforce, if the tablespace is not in quotas.

Oracle rounds a quota up to whole blocks of the tablespace, e.g. size: 1000 is stored as 8192 bytes with a block size of 8K. The comparison uses blocks, so the module is idempotent for such sizes.

User with quotas, all other quotas are removed
oracle_pdbs:
  - cdb: orcl
    pdb_name: ORCLPDB
    users:
      - schema: app
        state: present
        default_tablespace: app_data
        quotas_mode: enforce
        quotas:
          # without this entry, app has no quota on its default tablespace
          - tablespace: app_data
            size: unlimited
          - tablespace: app_index
            size: 500M
Note
 The old pull request for quotas in ansible-oracle-modules (#158) used a list of strings '<tablespace>:<size>'. This format is not supported, use {tablespace: <name>, size: <size>}.

1.18. oradb_rman: control_file_record_keep_time in init_parameters

control_file_record_keep_time defines, how many days the controlfile keeps the records of backups. Without RMAN catalog, RMAN knows only the backups in the controlfile: a value smaller than the recovery window makes backups unusable for RMAN, although they exist.

As of 5.0.0 oradb_rman asserts for every database with rman_jobs:

  • control_file_record_keep_time is defined in init_parameters (state: present, sid: '*'), and

  • the value is >= <n> for the retention policy RECOVERY WINDOW OF <n> DAYS (rman_retention_policy of the database or oradb_rman_retention_policy_default).

The playbook stops with a failed assert, when the parameter is missing or too small.

Example for RECOVERY WINDOW OF 14 DAYS
oracle_databases:
  - oracle_db_name: DB1
    rman_retention_policy: 'RECOVERY WINDOW OF 14 DAYS'
    init_parameters:
      - {name: control_file_record_keep_time, value: '30', scope: both, state: present}
    rman_jobs:
      - {name: parameter}

The assert can be disabled in emergency cases:

oradb_rman_assert_control_file_record_keep_time: false

1.21. local_listener in init_parameters of Single Instance databases

As of 5.0.0 the assert of oracle_databases in orasw_meta requires local_listener in init_parameters for every Single Instance database (with and without Oracle Restart) with state: present. RAC and RAC One Node databases are not checked, Clusterware sets local_listener.

Why:

DBCA sets local_listener to an alias, e.g. LISTENER_<DB_NAME>, and writes the alias into tnsnames.ora of the ORACLE_HOME (with Read-Only Oracle Homes in $ORACLE_BASE/homes/<oracle_home_name>/network/admin). After a switch of the ORACLE_HOME (Out-of-Place Patching, see out_of_place_patching.adoc) the alias is missing in tnsnames.ora of the new ORACLE_HOME. The instance cannot resolve local_listener and does not register its services at the listener (ORA-12514 for clients). An EZConnect address in local_listener needs no entry in tnsnames.ora.

Who is affected:

  • Inventories with a Single Instance database in oracle_databases without local_listener in init_parameters. The playbooks fail in the assert of orasw_meta:

    local_listener is missing in init_parameters of <oracle_db_name>, ...

Required actions:

  1. Add local_listener with EZConnect (//<host>:<port>) to init_parameters of the database. localhost and the port of the listener avoid an extra entry in tnsnames.ora.

  2. Add one address per listener, if the instance must register at more than one listener, e.g. '(ADDRESS_LIST=(ADDRESS=(PROTOCOL=TCP)(HOST=localhost)(PORT=1521))(ADDRESS=(PROTOCOL=TCP)(HOST=localhost)(PORT=1523)))'.

  3. Existing databases: oradb_manage_parameters changes local_listener with scope: both, the instance registers at the listener without restart. The entries of DBCA in tnsnames.ora are not removed by ansible-oracle.

Note
 localhost requires a listener on the loopback address. A listener with the hostname in HOST listens on all addresses of the host, unless IP=FIRST is set in listener.ora. Use the hostname or the address of the listener otherwise, e.g. //{{ ansible_hostname }}:1521.
Example
oracle_databases:
  - oracle_db_name: DB1
    oracle_db_type: SI
    listener_port: 1521
    init_parameters:
      - {name: local_listener, value: '//localhost:1521', scope: both, state: present}

1.22. oracle_databases: is_container and omf are true by default

As of 5.0.0 the attributes is_container and omf of oracle_databases are true by default. They need not to be defined in oracle_databases anymore.

Why:

26ai supports only Container Databases and ansible-oracle uses Oracle Managed Files for tablespaces by default. The defaults simplify the inventory.

Who is affected:

  • Inventories with a 19c database in oracle_databases without is_container. Before 5.0.0 a non-CDB was created, now a CDB is created. The tasks for PDBs (oradb_manage_pdb), the timezone upgrade (oradb_tzupgrade) and the switch of the ORACLE_HOME treat the database as CDB.

  • Inventories with a database in oracle_databases without omf. Before 5.0.0 dbca was called with -useOMF false, now with -useOMF true. omf is used during the creation of a database with dbca only.

Required actions:

  1. Set is_container: false for a 19c non-CDB.

  2. Use OMF for new databases. OMF is strongly recommended in ansible-oracle.

  3. Without OMF: set omf: false and use an own DBCA template without OMF (dbca_templatename). The DBCA templates of ansible-oracle are made for OMF. Databases without OMF are not tested anymore.

Example
oracle_databases:
  - oracle_db_name: DB1
    home: db19-si-ee
    is_container: false   # non-CDB, 19c only
    # not recommended and not tested:
    # omf: false          # dbca -useOMF false
    # dbca_templatename: <own DBCA template without OMF>

1.23. oracle_databases: db_create_file_dest and db_recovery_file_dest in init_parameters

As of 5.0.0 the assert of oracle_databases in orasw_meta requires db_create_file_dest and db_recovery_file_dest in init_parameters for every database with state: present and omf: true (default).

Why:

The parameters are needed in different situations, e.g. for dbca, standby databases (RMAN duplicate) and the directories of a new database. They are defined directly in init_parameters instead of deriving them from other variables. dbca uses the values for the datafile and recovery area destination. The global defaults oracle_dbf_dir_fs and oracle_reco_dir_fs are only used with omf: false (only storage_type: FS, own DBCA template, not tested).

Who is affected:

  • Inventories with a database in oracle_databases without db_create_file_dest or db_recovery_file_dest in init_parameters. The playbooks fail in the assert of orasw_meta:

    <oracle_db_name>: omf: true (default) needs db_create_file_dest and db_recovery_file_dest in init_parameters, ...

Required actions:

  1. Add db_create_file_dest and db_recovery_file_dest to init_parameters. Use the values of datafile_dest and recoveryfile_dest, if they were defined.

  2. Existing databases: use the current values of the database (show parameter db_create_file_dest, show parameter db_recovery_file_dest), otherwise oradb_manage_parameters changes them.

  3. Define db_recovery_file_dest_size before db_recovery_file_dest in init_parameters for existing databases without a recovery area (ORA-19802).

Example
oracle_databases:
  - oracle_db_name: DB1
    init_parameters:
      - {name: db_create_file_dest, value: '/u02/oradata', scope: both, state: present}
      - {name: db_recovery_file_dest_size, value: '10G', scope: both, state: present, dbca: false}
      - {name: db_recovery_file_dest, value: '/u02/fra', scope: both, state: present}

1.24. oracle_databases: datafile_dest and recoveryfile_dest are removed

As of 5.0.0 the attributes datafile_dest and recoveryfile_dest of oracle_databases are removed. They are redundant to db_create_file_dest and db_recovery_file_dest in init_parameters. datafile_dest in oracle_pdbs is not affected.

Who is affected:

  • Inventories with datafile_dest or recoveryfile_dest in oracle_databases. The playbooks fail in the assert of orasw_meta:

    <oracle_db_name>: datafile_dest and recoveryfile_dest in oracle_databases are removed. ...

Required actions:

  1. Move the values to db_create_file_dest and db_recovery_file_dest in init_parameters.

  2. Remove datafile_dest and recoveryfile_dest from oracle_databases.

  3. Databases with omf: false: the destinations are oracle_dbf_dir_fs and oracle_reco_dir_fs (global per host).

Before
oracle_databases:
  - oracle_db_name: DB1
    is_container: true
    datafile_dest: /u02/oradata
    recoveryfile_dest: /u02/fra
    init_parameters:
      - {name: db_create_file_dest, value: '/u02/oradata', scope: both, state: present}
After
oracle_databases:
  - oracle_db_name: DB1
    init_parameters:
      - {name: db_create_file_dest, value: '/u02/oradata', scope: both, state: present}
      - {name: db_recovery_file_dest, value: '/u02/fra', scope: both, state: present}

1.25. oracle_databases: omf false not allowed with ASM, oracle_dbf_dir_asm and oracle_reco_dir_asm removed

As of 5.0.0 the assert of oracle_databases in orasw_meta fails for a database with storage_type: ASM and omf: false. ASM without OMF makes no sense in practice. The variables oracle_dbf_dir_asm and oracle_reco_dir_asm are removed, the disk groups are taken from db_create_file_dest and db_recovery_file_dest in init_parameters.

oradb_rman: the templates parameter_rac and parameter_fra_disk use db_create_file_dest from init_parameters for the snapshot controlfile instead of oracle_dbf_dir_asm. Before, parameter_fra_disk created a wrong name with two ` (`+DATA).

Who is affected:

  • Inventories with a database with storage_type: ASM and omf: false. The playbooks fail in the assert of orasw_meta:

    <oracle_db_name>: omf: false is not allowed with storage_type: ASM. ...

  • Inventories with oracle_dbf_dir_asm or oracle_reco_dir_asm. The variables have no effect anymore.

Required actions:

  1. Remove omf: false from ASM databases and add db_create_file_dest and db_recovery_file_dest to init_parameters.

  2. Remove oracle_dbf_dir_asm and oracle_reco_dir_asm from the inventory.

Example
oracle_databases:
  - oracle_db_name: DB1
    storage_type: ASM
    init_parameters:
      - {name: db_create_file_dest, value: '+DATA', scope: both, state: present}
      - {name: db_recovery_file_dest_size, value: '10G', scope: both, state: present, dbca: false}
      - {name: db_recovery_file_dest, value: '+FRA', scope: both, state: present}

1.26. oracle_databases: max_pdbs in init_parameters of Container Databases

As of 5.0.0 the assert of oracle_databases in orasw_meta fails for a Container Database (is_container: true, default as of 5.0.0) with state: present without max_pdbs in init_parameters (without sid or sid: '*'). max_pdbs defines explicitly how many PDBs are allowed by the license. The value must be an integer:

Edition (db_homes_config) Maximum max_pdbs Remark

SE2 (SE)

3

EE

1024

More than 3 PDBs require a license for the Multitenant Option!
Important
 Enterprise Edition without a license for the Multitenant Option allows only 3 PDBs, like Standard Edition 2. ansible-oracle has no switch for licensed options yet, so the assert allows up to 1024 PDBs for EE. Check your license before you set max_pdbs greater than 3.

Who is affected:

  • Inventories with a Container Database without max_pdbs in init_parameters, or with a value greater than 3 (SE2) or 1024 (EE). This includes 19c databases without is_container, which are Container Databases as of 5.0.0. The playbooks fail in the assert of orasw_meta:

    <oracle_db_name>: is_container: true (default) needs max_pdbs in init_parameters with an integer value <= <limit> for edition <edition> ...

Required actions:

  1. Add max_pdbs with the number of PDBs allowed by your license to init_parameters. max_pdbs is set by dbca for a new database and changed by oradb_manage_parameters for an existing database.

Example
oracle_databases:
  - oracle_db_name: DB1
    init_parameters:
      - {name: max_pdbs, value: '3', scope: both, state: present}

1.27. oracle_databases: control_management_pack_access in init_parameters of Enterprise Edition databases

As of 5.0.0 the assert of oracle_databases in orasw_meta fails for a database of an Enterprise Edition home (edition: EE in db_homes_config) with state: present without control_management_pack_access in init_parameters (without sid or sid: '*'). control_management_pack_access defines explicitly which Management Packs are licensed. Without the parameter, the Oracle default for Enterprise Edition is DIAGNOSTIC+TUNING, which needs a license for the Diagnostics and Tuning Pack.

Value License

NONE

no Management Pack

DIAGNOSTIC

Diagnostics Pack

DIAGNOSTIC+TUNING

Diagnostics Pack and Tuning Pack

The parameter is optional for Standard Edition 2. If it is defined, the value must be NONE, the Management Packs are not available for Standard Edition 2.

Important
 Set the value according to your license. The Management Packs are options of the Enterprise Edition. ansible-oracle has no switches for licensed options yet. Check if further settings are needed for your licensed options.

Who is affected:

  • Inventories with a database of an Enterprise Edition home without control_management_pack_access in init_parameters, or with another value than NONE, DIAGNOSTIC or DIAGNOSTIC+TUNING.

  • Inventories with a database of a Standard Edition 2 home with control_management_pack_access other than NONE. The playbooks fail in the assert of orasw_meta:

    <oracle_db_name>: control_management_pack_access in init_parameters must be one of NONE, DIAGNOSTIC or DIAGNOSTIC+TUNING and is mandatory for Enterprise Edition ...

Required actions:

  1. Add control_management_pack_access with the value allowed by your license to init_parameters. For an existing database, oradb_manage_parameters changes the parameter to the value from the inventory.

Example
oracle_databases:
  - oracle_db_name: DB1
    init_parameters:
      - {name: control_management_pack_access, value: 'NONE', scope: both, state: present}

1.28. oracle_databases: sga_target and pga_aggregate_target in init_parameters

As of 5.0.0 the assert of oracle_databases in orasw_meta fails for a database with state: present without sga_target or pga_aggregate_target in init_parameters. These are the essential memory parameters of an Oracle database and must be defined explicitly. Entries with sid are accepted (instance specific values for RAC).

oracle_db_mem_totalmb (totalMemory in dbca) is not supported anymore, the assert fails if it is set. Before, the assert required either oracle_db_mem_totalmb or sga_target in init_parameters.

Who is affected:

  • Inventories with a database without sga_target or pga_aggregate_target in init_parameters, or with oracle_db_mem_totalmb. The playbooks fail in the assert of orasw_meta:

    <oracle_db_name>: sga_target and pga_aggregate_target are essential memory parameters and must be defined in init_parameters ...

Required actions:

  1. Add sga_target and pga_aggregate_target to init_parameters.

  2. Remove oracle_db_mem_totalmb.

Example
oracle_databases:
  - oracle_db_name: DB1
    init_parameters:
      - {name: sga_target, value: '2G', scope: spfile, state: present}
      - {name: pga_aggregate_target, value: '512M', scope: both, state: present}

1.29. oracle_databases: no memory_target and memory_max_target with Hugepages

As of 5.0.0 the assert of oracle_databases in orasw_meta fails for a database with state: present with memory_target or memory_max_target in init_parameters (also with sid) if Hugepages are configured (configure_hugepages: true, default of orahost). Automatic Memory Management (AMM) prevents the usage of Hugepages. Entries with state: absent are allowed to remove the parameters from the spfile.

Who is affected:

  • Inventories with a database with memory_target or memory_max_target in init_parameters and without configure_hugepages: false. The playbooks fail in the assert of orasw_meta:

    <oracle_db_name>: memory_target and memory_max_target are not allowed in init_parameters with Hugepages ...

Required actions:

  1. Use sga_target and pga_aggregate_target (Automatic Shared Memory Management) instead of AMM.

  2. Set state: absent for memory_target and memory_max_target to remove them from the spfile of existing databases, or set configure_hugepages: false if Hugepages are not used.

Example
oracle_databases:
  - oracle_db_name: DB1
    init_parameters:
      - {name: memory_target, value: '0', scope: spfile, state: absent}
      - {name: memory_max_target, value: '0', scope: spfile, state: absent}
      - {name: sga_target, value: '2G', scope: spfile, state: present}
      - {name: pga_aggregate_target, value: '512M', scope: both, state: present}

1.30. Role oraswahf_install replaced by ahf

The role oraswahf_install was an empty placeholder for the installation of Oracle Autonomous Health Framework (AHF) - it had no tasks and no variables. It is removed and replaced by the new role ahf, which installs, upgrades and configures AHF. The central web interface AHF Fleet Insights is installed with the new role ahf_fleet_insights.

Note
 AHF is not installed by oraswahf_install, existing installations are not affected. Only playbooks, which reference the role, fail with the role 'oraswahf_install' was not found.
Before: own playbook
- hosts: dbfs
  become: true
  roles:
    - opitzconsulting.ansible_oracle.oraswahf_install
After: own playbook or playbooks/ahf.yml
- hosts: dbfs
  become: true
  roles:
    - opitzconsulting.ansible_oracle.ahf

The variables and the decisions for an installation are described in Oracle Autonomous Health Framework (AHF).
