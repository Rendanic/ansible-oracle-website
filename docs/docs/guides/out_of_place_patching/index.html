Out-of-Place Patching - Switch ORACLE_HOME

Important
 Out-of-Place Patching is supported for Single Instance primary databases without Grid Infrastructure/Oracle Restart only.
The guide describes the concept, all dependencies and the gaps in the current implementation.

Out-of-Place Patching switches a database from its current ORACLE_HOME to another, already installed and patched ORACLE_HOME. The installation and patching of the new ORACLE_HOME is not part of Out-of-Place Patching. It is done before with other roles (oraswdb_install, oraswdb_manage_patches or from a Golden Image).

Advantages compared to In-Place Patching with opatch apply:

  • The new ORACLE_HOME is installed and patched before the switch without downtime, because no database is running from it.

  • The downtime is reduced to a restart of the database and datapatch.

  • Fallback is easy: the old ORACLE_HOME is still available.

Note
 A Golden Image is recommended, but not required.
The new ORACLE_HOME can also be installed and patched with ansible-oracle on the database server. The switch of the database is independent from the way the new ORACLE_HOME was created. See Preparation of the new ORACLE_HOME.

1. Requirements

  • Oracle Database 19c or newer

  • Read-Only Oracle Homes (readonly_home: true) are recommended, but not required

    • Configuration files like SPFile and password file are not part of the ORACLE_HOME and are shared between all Read-Only `ORACLE_HOME`s.

    • The switch copies SPFile, PFile and password file, when the location differs between old and new ORACLE_HOME (e.g. switch from a Read-Write into a Read-Only ORACLE_HOME).

    • readonly_home must not be changed for an installed ORACLE_HOME.

  • Each Read-Only ORACLE_HOME needs 2 attributes in db_homes_config:

    db_homes_config:
  db1932-si-ee:
    readonly_home: true
    oracle_home_name: db1932siee

  • oracle_home_name is mandatory:

    • It cannot be derived from the key in db_homes_config. Oracle allows only characters, numbers and _ in the name of an ORACLE_HOME in the Oracle Inventory. YAML keys are much less restrictive (e.g. db1932-si-ee is a valid key, but not a valid oracle_home_name).

    • It must be unique over all ORACLE_HOME`s on a server. It defines the `ORACLE_BASE_HOME ($ORACLE_BASE/homes/<oracle_home_name>), which must not be shared between the old and the new ORACLE_HOME.

  • Enough disk space for at least 2 `ORACLE_HOME`s at the same time

2. Read-Only Oracle Home

A Read-Only Oracle Home separates the software from the configuration. The locations are reported by orabasehome and orabaseconfig.

3. Process overview

  1. Prepare the new ORACLE_HOME (no downtime)

    1. Install the new ORACLE_HOME with oraswdb_install / oraswdb_manage_patches (not part of Out-of-Place Patching), one of:

      1. from a Golden Image (recommended)

      2. from the base release, followed by opatch apply for all patches

    2. Create the network configuration in the new ORACLE_BASE_HOME

  2. Switch the database (downtime) - Out-of-Place Patching with oradb_manage_db

    1. Stop the database (and listener) from the old ORACLE_HOME

    2. Change the ORACLE_HOME in /etc/oratab or in Oracle Clusterware (srvctl)

    3. Start the listener and database from the new ORACLE_HOME

    4. Execute datapatch

  3. Post tasks

    1. APEX, time zone, statistics, etc. (optional)

    2. Remove the old ORACLE_HOME after a successful test period

4. Preparation of the new ORACLE_HOME

The new ORACLE_HOME can be prepared in 2 ways. Both are supported by ansible-oracle and both lead to the same result for the switch.

Recommendation: download the Golden Image created by Oracle with the role autoupgrade (gold_image in autoupgrade_download_patches or autoupgrade_download_gold_image). This is the way with the least effort, because no ORACLE_HOME has to be installed and patched for creating the Golden Image.

Alternative: create the Golden Image once from an ORACLE_HOME installed and patched by ansible-oracle (role oraswdb_golden_image), e.g. when one-off patches are needed, which are not part of the Golden Image from Oracle.

Use the Golden Image for all servers.

Important
 The implementation of the switch must not depend on the way the new ORACLE_HOME was prepared.
The only requirement for the switch is an installed and fully patched ORACLE_HOME.

5. Dependencies

5.1. Registration of the ORACLE_HOME

Table 3. Registration of the ORACLE_HOME for a database
Environment Registration Switch

Single Instance without GI

/etc/oratab

Replace the line <SID>:<old ORACLE_HOME>:<Y/N> with the new ORACLE_HOME.

Oracle Restart

Oracle Clusterware (OCR/OLR)

srvctl modify database -db <db_unique_name> -oraclehome <new ORACLE_HOME>
/etc/oratab is maintained by Oracle Clusterware.

Oracle RAC

Oracle Clusterware (OCR)

Rolling switch node by node. Not covered in this guide yet.

The following parts of ansible-oracle read the ORACLE_HOME from /etc/oratab and follow the switch automatically:

  • systemd service / manage_oracle_rdbms_procs.sh (start/stop of databases)

  • ocenv / .profile_<ORACLE_SID>

  • rman_backup.sh from role oradb_rman

5.2. Stop and Start

  • The database must be stopped from the old ORACLE_HOME.

  • With Oracle Restart/RAC the stop must be done with srvctl from the old ORACLE_HOME, before srvctl modify database is executed.

  • The start is done from the new ORACLE_HOME.

5.3. Listener

  • A listener running from the database ORACLE_HOME must be restarted from the new ORACLE_HOME.

  • All databases served by this listener must be switched together. Recommendation: run the listener from Grid Infrastructure or from a dedicated ORACLE_HOME.

  • Static registrations in SID_LIST_<LISTENER> contain the ORACLE_HOME:

    • Data Guard Broker (<db_unique_name>_DGMGRL)

    • extproc

    • Static service entries

5.4. Network configuration and wallets

  • sqlnet.ora, tnsnames.ora and listener.ora must exist in $ORACLE_BASE/homes/<new oracle_home_name>/network/admin. Alternative: a central TNS_ADMIN.

  • WALLET_LOCATION or ENCRYPTION_WALLET_LOCATION in sqlnet.ora must not point into the old ORACLE_HOME.

  • TDE with the init parameter WALLET_ROOT is independent from the ORACLE_HOME.

5.5. datapatch

  • datapatch is mandatory after the start from the new ORACLE_HOME.

  • datapatch must be executed for the CDB and all PDBs.

  • OJVM patches may need a startup in upgrade mode, depending on the release.

  • Data Guard: datapatch is executed on the primary database only.

5.6. Directory objects

Directory objects can point into the old ORACLE_HOME. The OPatch directories are changed by datapatch, own directories are not.

Find directory objects in the old ORACLE_HOME
select directory_name, directory_path
from dba_directories
where directory_path like '/u01/app/oracle/product/19/db19_2601%';

5.7. Content of the ORACLE_HOME

The new ORACLE_HOME must contain all customizations of the old ORACLE_HOME:

  • Relink options (e.g. Unified Auditing, dNFS) - included in a Golden Image or set by oraswdb_install

  • One-off patches - included in a Golden Image or defined in db_homes_config[].opatch for the new ORACLE_HOME

  • oranfstab

  • Custom DBCA templates

5.8. Data Guard

  • The standby databases are switched first.

  • The primary database is switched afterwards, followed by datapatch.

  • Static listener registrations for the Data Guard Broker must be changed (see Listener).

5.8.1. Physical Standby

Important
 Not implemented yet.
The current implementation opens every database after the switch and executes datapatch.

A physical standby database must be handled differently from a primary database:

  • The standby database is started in MOUNT only. Opening the database while Redo Apply is running uses Active Data Guard, which needs an extra license. This is valid even when the standby database was opened READ ONLY WITH APPLY before the switch.

  • datapatch must not be executed on a standby database. The SQL changes are applied with Redo Apply from the primary database.

The role of the database is read after startup mount from the controlfile:

startup mount
select database_role from v$database;
Table 4. Actions after startup mount depending on DATABASE_ROLE
DATABASE_ROLE Open database datapatch

PRIMARY

yes (+ all PDBs)

yes

PHYSICAL STANDBY

no, remains in MOUNT

no

Redo Apply after the switch:

  • With Data Guard Broker (dg_broker_start=TRUE) the broker restarts Redo Apply automatically.

  • Without Data Guard Broker Redo Apply must be restarted manually. ansible-oracle does not start Redo Apply, because it does not manage Data Guard configurations.

    alter database recover managed standby database disconnect;

5.9. External dependencies

  • Enterprise Manager and other monitoring targets

  • Scripts and crontabs with a hard coded ORACLE_HOME

  • Applications with a local ORACLE_HOME (e.g. Bequeath connections)

6.2. Gaps

Table 6. Missing features for Out-of-Place Patching
Gap Location Description

Incomplete check of oracle_home_name

roles/oraswdb_install/tasks/roohctl.yml

Only the existence of oracle_home_name is checked for readonly_home: true, and only during the installation. Missing: check for allowed characters, unique value over all ORACLE_HOME`s in `db_homes_installed, check in orasw_meta before any change on the server.

6.3. ORACLE_HOME without database

An ORACLE_HOME in db_homes_installed without a database in oracle_databases is a valid configuration:

  • The new ORACLE_HOME has no database before the switch.

  • The old ORACLE_HOME has no database after the switch, until it is removed.

  • Listeners can run from a dedicated ORACLE_HOME without database.

The oracle_db_type must still be identical for all databases in the same ORACLE_HOME. All roles and asserts must support an ORACLE_HOME without database.

7. Inventory example

The ORACLE_HOME for each Release Update gets its own entry in db_homes_config with a unique oracle_home and oracle_home_name. Both ways to prepare the new ORACLE_HOME can be mixed, e.g. the old ORACLE_HOME from a Golden Image and the new one installed and patched on the server.

Example db_homes_config with Golden Image
db_homes_config:
  db19_2601:
    version: 19.3.0.0
    oracle_home: /u01/app/oracle/product/19/db19_2601
    oracle_home_name: db19_2601
    readonly_home: true
    edition: EE
    imagename: db_home_19.30.zip
Example db_homes_config installed and patched on the server
db_homes_config:
  db19_2604:
    version: 19.3.0.0
    oracle_home: /u01/app/oracle/product/19/db19_2604
    oracle_home_name: db19_2604
    readonly_home: true
    edition: EE
    opatch_minversion: 12.2.0.1.48
    opatch:
      - patchid: <RU patch id>
        # Database Release Update 19.31
        state: present
      - patchid: <OJVM patch id>
        # Oracle JavaVM Component Release Update 19.31
        state: present
Note
 stop_processes is not needed for the patches of the new ORACLE_HOME.
Example: switch of database ORCL from db19_2601 to db19_2604
db_homes_installed:
  - home: db19_2601
    state: present
  - home: db19_2604
    state: present

oracle_databases:
  - home: db19_2604    # (1)
    oracle_db_name: ORCL
    state: present

  1. Changing home is the trigger for the switch. See Existing features.
